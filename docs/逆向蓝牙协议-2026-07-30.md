# SHAKI 小程序 BLE 协议整理

来源：`D:\work buddy\2026-07-30-02-37-08` 内的 `SHAKI小程序逆向分析报告.html` 与解包后的 `wxunpack\output_shaki\app-service.js`。

## 已确认

- 连接模式：微信小程序 Central BLE，调用 `createBLEConnection({ deviceId, timeout: 1500 })`。
- 扫描：`startBluetoothDevicesDiscovery({ allowDuplicatesKey: true })`，过滤 `RSQ-APP01`；SHAKI 主题还使用 `XQ_` 设备名前缀。
- 服务：连接后读取服务列表，选择 UUID 字符串中包含 `FFA0` 的服务。完整 UUID 未在静态包中硬编码，必须以真机返回值为准。
- 特征：调用 `getBLEDeviceCharacteristics` 后保存特征列表；写入路径取列表第一个特征的 UUID。
- 写入：`writeBLECharacteristicValue`，ArrayBuffer 为 5 字节，无 A5 魔数、无 CRC。
- 断开：设备连接超时配置为 1500ms；2.4G 虚拟设备通过设备 ID 前缀 `RSQ2.4` 分支处理。

## 5 字节写入帧

```text
[0] brand       SHAKI = 0xAB, default = 0xAA
[1] function    default = 0x0B
                heat = 0x0C
                electric = 0x0D
                strike = 0x0F
                clock = 0x10
[2] motor       电机编号，默认 0x01
[3] level       档位，代码默认值为 5
[4] strength    强度，代码默认值为 1
```

例：SHAKI、默认功能、电机 1、档位 5、强度 1：`AB 0B 01 05 01`。

源码先用 `Number(value).toString(16).padStart(2, '0').toUpperCase()` 做日志格式化，随后通过 `DataView.setUint8` 写入，因此最终发送的是上面的原始字节。

## 2.4G 广播分支

静态代码还存在 Peripheral 广播路径：

- 广播负载沿用前 5 字节；`clock` 模式追加 `0x99`。
- 非 iOS 分支使用 manufacturer ID `0xFFA0`。
- iOS 分支使用 manufacturer ID `0xA0FF`，并将负载反向拼入由 `getServiceUUIDs(payload, 'A0FF')` 生成的 service UUID 列表。

## 未确认项

- `FFA0` 对应的完整 128-bit UUID。
- 写特征是否同时支持 notify；静态代码的通知路径使用了独立的 store 字段，不能仅凭静态包确定最终特征 UUID。
- 每个电机编号与实际物理通道的映射。
- 设备回传帧的完整格式；静态代码只把通知数据转为字节数组并读取其中的压力值。

## 与演示协议的区别

`pulse-miniprogram/config/ble-config.js` 中的 `A5 / FFE0 / FFE1 / CRC8` 是另写的演示协议，文件注释明确写着“自有协议设计”，并且引用的 `utils/ble-manager.js` 不存在。它不能覆盖上述从已解包 `app-service.js` 提取出的真实协议证据。

## App 接入边界

`src/services/legacyBleProtocol.js` 只负责帧编码、解码和 UUID/特征选择，不调用微信 `wx.*` API。当前 HeartSync Web/PWA 仍使用模拟设备服务；接入原生 Capacitor 或微信小程序时，再将它挂到平台 BLE adapter，并在真机上记录服务/特征列表后补齐未确认项。
